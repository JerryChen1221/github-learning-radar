# 从研究报告到图文分享

## 先复用已有材料

输入可以是本次研究报告、用户提供的旧报告或一篇已有文章。已有材料足够时不重新搜索或拉取仓库；仅在用户要求更新、关键事实不明确或涉及当前产品使用方法时核实相应一手来源。

先确定读者和主问题。保持原稿，默认在 `articles/<artifact_id>/` 创建新稿；用户明确要求原位编辑时才修改指定原稿。

## 写作结构

可以参考 [文章模板](../assets/article-template.md)，但根据篇幅和读者合并章节，不机械保留所有标题：

1. 用一个真实的问题开场，说明研究为什么值得做。
2. 回答项目是什么、适合什么、不负责什么；比较要看设计取舍。
3. 用一两个有固定版本证据的机制支撑判断，不堆功能词汇。
4. 说明这些机制如何回答当前学习问题，提出一个最小实验。
5. 交代完成范围与未验证项，保留来源和时间。
6. 分享方法时再解释 Skill、画像、历史与定时器的不同职责，以及别人如何替换成自己的输入。

语言自然、专业，不用泛泛的“AI 赋能”替代具体判断。不把未来设想写成已经实践，不把 `partial` 报告润色成完整验证成功。用户画像是选题依据，不是要公开的正文；对分享稿只保留用户要求公开的抽象问题，不带入聊天摘录、个人路径、内部标识或配置值。

## 配图与文件

按 [配图指南](diagram-guide.md) 为实际需要解释的关系绘制 SVG，通常 1—3 张即可。是否使用预算、Runtime 或评测图，取决于文章内容；不要把 Agent 主题强加给数据库或其他领域的研究。

默认交付结构：

```text
articles/<artifact_id>/
├── article.md
├── article.html           # 需要本地阅读或富文本粘贴时生成
├── editor-body.html       # 只有正文，不重复包含页面标题
└── diagrams/
    ├── workflow.svg
    └── workflow.png       # 渲染能力可用时提供兼容图
```

目录示例是产物说明，不应原样作为正文。未生成 HTML 或 PNG 就不创建空文件，也不把不存在的文件写进记录。

Markdown 的配图使用能随目录搬迁的相对路径。离线文章的 SVG 可直接引用；PNG 未生成时不要留下 PNG 链接。HTML 转换优先使用已有的可信渲染能力；不为简单分享引入前端工程或远程脚本。对代码示例做 HTML 转义，保持代码块、表格、列表和引用完整。

网页使用的 `editor-body.html` 只包含正文和编辑器能保留的语义标签。上传配图后将其替换成页面实际产生的地址；不能将本地相对路径、`file://`、临时 blob 地址或本机绝对路径当成读者能访问的附件链接。

## 检查与交付

- 逐项核对项目身份、SHA、来源日期、证据强弱；不在改写中悄悄更新或混合数据。
- 查看 SVG/PNG 的实际渲染效果，确认中文、长文本、箭头、对齐与阅读尺寸。
- 检查文章的图片和附件确实存在，代码围栏和表格闭合，无模板占位符。
- 本地分享包只放文章及需要的图片；Skill 安装包单独打包，不夹带私人画像、运行 JSON、网页截图或完整仓库。
- 如用户仅要求本地图文稿，到这里结束。仅有文章中的示例网址或自动化说明，不构成写网站或建定时器的请求。

如用户明确要求网页交付，接 [网页流程](web-delivery.md)；明确要求实际配置定时，接 [定时流程](automation-workflow.md)。
